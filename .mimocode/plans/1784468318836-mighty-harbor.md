## HIGH Severity (3 bugs)

### H1. `ref.invalidate` + immediate `ref.read` returns stale data
- **File**: `lib/presentation/pages/medication/widgets/edit_medication_dialog.dart:125-126`
- **Problem**: After saving a medication, `ref.invalidate(medicationsProvider)` is called, then immediately `ref.read(medicationsProvider).value ?? []` reads the OLD cached data. The subsequent `rescheduleMedicationReminders` and `rescheduleRefillReminders` operate on stale medication list.
- **Fix**: Replace with `await ref.refresh(medicationsProvider.future)` to get the updated data before rescheduling.

### H2. `ref.read(medicationsProvider).value` stale after DB update
- **File**: `lib/presentation/pages/medication/widgets/medications_list_widget.dart:214`
- **Problem**: Same pattern as H1. After `updateRefill()`, the code reads the StreamProvider's current synchronous value which hasn't updated yet. `rescheduleRefillReminders` operates on old data.
- **Fix**: Same approach — `await ref.refresh(medicationsProvider.future)`.

### H3. `rescheduleMedicationReminders` cancel range silently kills snooze notifications
- **File**: `lib/core/data/services/notification_service.dart:201-207`
- **Problem**: Cancel range `[2000, 202000)` includes snooze IDs starting at 4000. When medication reminders are rescheduled (e.g., user edits a medication), any active "snooze 5 minutes" notification is silently cancelled.
- **Fix**: Either narrow the cancel range to exclude snooze base ID (4000), or preserve snooze IDs during reschedule by checking the snooze range before cancelling.

## MEDIUM Severity (5 bugs)

### M1. `watchTodayCheckIn` / `watchTodayMoodEntries` stale after midnight
- **File**: `lib/core/data/database/app_database.dart:137-154, 326-341`
- **Problem**: `DateTime.now()` is captured once at stream construction. After midnight, the SQL filter still references yesterday's date range. The existing midnight invalidation on `streakSummaryProvider` fixes this for the provider layer, but any direct consumer of these streams without invalidation gets stale data.
- **Fix**: This is a known issue with a provider-level workaround. Document that all consumers must invalidate on midnight, or change to a non-baked-date stream pattern.

### M2. `_isWeekPerfect` rejects users with late-night double check-ins
- **File**: `lib/domain/logic/care_engine.dart:201-208`
- **Problem**: First loop rejects anyone with ANY check-in at hour >= 22 in the 7-day window, even if they ALSO checked in before 22:00 that same day. A user who checks in at 10:00 and 23:00 daily would never get the "week perfect" celebration.
- **Fix**: Remove the first loop entirely. The second loop (line 210-219) already correctly checks that each day has at least one check-in before 22:00.

### M3. Mixed `ctx` (dialog) and `context` (page) after async gap
- **File**: `lib/presentation/pages/settings/settings_page.dart:465-479`
- **Problem**: After `await service.importFromJson(input)`, the code checks `ctx.mounted` (dialog context) but then uses outer `context` for `ScaffoldMessenger.of(context)`. If the page was disposed during import, this throws.
- **Fix**: Add `if (!context.mounted) return;` before using the outer `context`, or use `ctx` for all context-dependent calls.

### M4. `Future.delayed` timer not cancelled on widget dispose
- **File**: `lib/presentation/pages/home/home_page.dart:417-419`
- **Problem**: `_showCelebrationOverlay` creates a `Future.delayed` that is not stored or cancelled on dispose. If the widget is disposed and recreated within 1800ms, the old future could remove a newly created overlay entry.
- **Fix**: Store the timer/future and cancel in `dispose()`.

### M5. `TextEditingController` leaked on early return path
- **File**: `lib/presentation/pages/settings/settings_page.dart:426, 507`
- **Problem**: Controller is created before `showDialog` but only disposed in `.then()`. If `context.mounted` check fails and the method returns early, the controller is never disposed.
- **Fix**: Dispose the controller in the early return path, or create it inside the builder.

## LOW Severity (6 bugs)

### L1. Notification ID collision for >10 time slots per medication
- **File**: `lib/core/data/services/notification_service.dart:226`
- **Problem**: Formula `med.id * 10 + i` only reserves 10 slots. >10 times per medication causes ID collision.
- **Fix**: Use `* 20` or add an assertion.

### L2. `rescheduleRefillReminders` overlaps medication IDs for medId >= 400
- **File**: `lib/core/data/services/notification_service.dart:482-487`
- **Problem**: Refill cancel range `[6000, 206000)` overlaps medication reminder IDs when `medId >= 400`.
- **Fix**: Increase refill base ID or separate the ranges more clearly.

### L3. `saveSetup()` calls `DateTime.now()` twice in same transaction
- **File**: `lib/core/data/database/app_database.dart:392, 409`
- **Problem**: Two separate `DateTime.now()` calls in the same transaction body. Could produce different dates if spanning midnight.
- **Fix**: Cache once at top of transaction.

### L4. SharedPreferences async read-after-write
- **File**: `lib/core/data/services/assessment_reminder_service.dart:143, 149`
- **Problem**: `setLastAssessmentAt(realLast)` then immediately `getLastAssessmentAt()` — async read-after-write race on SharedPreferences.
- **Fix**: Use local variable directly instead of re-reading.

### L5. `_onCheckIn` takes BuildContext parameter across async gap
- **File**: `lib/presentation/pages/home/home_page.dart:287`
- **Problem**: Method takes `BuildContext context` as parameter instead of using `this.context`. Noted in AGENTS.md as a known anti-pattern.
- **Fix**: Remove parameter, use `this.context`.

### L6. `vent_detail_page` stale `_tempDecryptedPath` on entry update
- **File**: `lib/presentation/pages/vent/vent_detail_page.dart:94`
- **Problem**: If entry data updates while audio is paused, `_tempDecryptedPath` still points to old file.
- **Fix**: Reset `_tempDecryptedPath` when entry data changes.
