## 1. 🔴 P0 风险点(必看 — 不修可能拒上架或被监管)

### 1.1 失联通知业务暂停的合规性(最大灰色地带)

**现状**:
- `privacy_policy.md §0.5 / §3 / §12` 描述"失联通知会发 SMS 给紧急联系人"
- `user_agreement.md §1` 写"失联通知(**规划中,本版本未启用**)"
- `feature_flags.dart:35` `_prodEmergencyContactEnabled = false` 整段关闭
- 用户加联系人入口**仍开放**,但实际**不触发任何通知**

**问题**:
- **PIPL §17**:处理目的 / 方式 / 范围应**明确告知**。用户读到隐私政策以为"加了联系人就会发",实际 100% 不发 = **告知不准确**
- **Apple 5.2.1 / 5.2.3**:应用描述与功能不符(App Store 拒 4.3 Spam 风险)
- **不真实宣传风险**:用户以为 App 监控自己,实际 100% 不监控 — 心理预期错位,出事家属骂 App 假宣传

**法务需确认**:
1. 隐私政策 + 用户协议中"失联通知规划中"的措辞是否够强,能否在 Apple / Google 审核 + 监管询问时站得住
2. 是否需要在**主页 / 紧急联系人 section 顶部**加显眼 banner(技术已 R82 准备,需 UX 决策)
3. **v0.27 release 不开 / v0.28 接入 SMS 后开**的切换,文案是否需统一升级

### 1.2 紧急联系人"单独同意"链路不完整(PIPL §23 风险)

**现状**(privacy_policy §12 实施进度表):
- ✅ 用户本人同意(v0.22)
- ✅ "已告知"勾选(v0.22)
- ✅ 软告知弹窗(R66)
- ⏸ **联系人本人回复 Y 确认** — **业务整体暂停, 依赖 SMS provider 真接**
- ✅ 同意记录可审计
- ✅ 撤回同意业务层真接(R67)

**问题**:
- 严格按 PIPL §23"向第三方提供 PII 前应**单独告知第三方**",**未回复 Y = 未真正单独告知** = 中度合规风险
- 隐私政策自评"法律风险等级:中"(`privacy_policy §12 末段`)
- 法务需评估:在**业务暂停期间**,R66 的"软告知"是否能作为合规抗辩?需不需要**完全移除"失联通知"在所有渠道的描述**,只写"未来规划"?

### 1.3 8 元买断 IAP 暂停 + 文档写明 = 文案 / 实际不符

### 1.4 数据导出 0 consent 流程(PIPL §13/§44)

**法务需确认**:

### 1.6 隐私 / PIPL 投诉邮箱软隐藏(PIPL §50)

**现状**:
- `privacy_policy §9` + `user_agreement §8`:**本服务不提供邮件渠道**,软隐藏 `privacy@chroniccare.app`
- 用户通过 App 内 "设置 → 法律与隐私" 行使 PIPL §14 撤回同意权
- `docs/LEGACY_API_NOTES.md` 软隐藏决策

**问题**:
- **PIPL §50** 个人信息处理者**应**提供**便捷的**权利行使渠道 + **明确**的联系方式 — 软隐藏邮箱是否算"便捷"?
- **未成年人 7 个工作日内响应删除请求**(`privacy_policy §10`) — 软隐藏邮箱,怎么响应?
- **Apple 5.1.1**:应用必须有可访问的"支持 URL" + 隐私 URL

**法务需确认**:
1. 软隐藏邮箱是否合规?还是必须**注册 `privacy@chroniccare.app` 邮箱**真接收 + 7 工作日响应?
2. App 内"法律与隐私"页是否够"便捷"?(需要测用户操作流程)
3. 注册邮箱 + 真正接收的过渡方案(SOP 已在 `docs/STOREFRONT_RELEASE_SOP.md`)

### 1.7 树洞录音"特殊类别敏感数据"处理

**现状**(`sensitive_data_consent §2.2`):
- 树洞录音 = 树洞是**最高敏感**的数据
- 录音存放在 App 私有目录,AES-256 加密(密钥与数据库密钥独立管理)
- 树洞内容**绝不**进入趋势 / 评估 / 失联检测 / 通知 / 任何统计
- 树洞**不**包含在"导出 JSON"中(只导出文字)

**问题**:
- 树洞属"精神心理类表达",在 PIPL §28 敏感个人信息定义中**不一定属于"医疗健康"** — 但属"私密记录"应被保护
- 法务需明确:**树洞是"敏感个人信息"吗?**归类决定同意流程 + 撤回流程的强度
- 当前同意流程 = 整个 App 一次同意 3 文件。树洞撤回走 `ConsentKind.vent` 单独 toggle(R67)
- **撤回 vent 同意后,旧树洞是否删除?**(R67 决定:数据**不删除**,可重新开启)— 法务需评估是否合规 PIPL §47(删除权)

**法务需确认**:
1. 树洞是否归类"敏感个人信息"
2. 撤回 vent 同意后保留旧数据是否合规(还是必须立即物理删除)
3. 加密强度是否够(PIPL §51 加密要求:算法 + 密钥管理)

## 2. 🟡 P1 关注点(中度风险,过审可加但建议修)

- 是否需要明确"不收集设备 ID / IMEI / AAID / 广告 ID"?

### 2.2 树洞数据导入策略

**现状**(`sensitive_data_consent §2.2`):
- 树洞数据导入后,会作为新条目添加(不会覆盖现有树洞)

**问题**:
- 用户 A 导出 JSON → 加密 U 盘 → 用户 B 导入 → 用户 A 的树洞是否会泄露到用户 B?(取决于 ConsentKind 是否按设备绑定)
- 当前 import 逻辑:每条都是独立 entry,无 contactId 关联

**法务需确认**:
1. 树洞导出 / 导入是否要加"设备绑定"保护
2. 多设备登录场景:用户加新设备时,旧设备树洞是否自动同步?(当前**不同步**,本地存储)

### 2.3 算法偏见 / 失联检测的"误判"风险

**现状**:
- 失联检测算法:`streak_calculator.dart` / `care_engine.dart` 多 strategy(连续 N 天 / 周末 / 节假日等)
- 误判 = 用户其实没事但被通知家人 = 心理负担 + 家人不必要的焦虑

**问题**:
- 算法需要提供"反馈机制":误判时用户可"标记这不是失联"
- 隐私政策是否需加"算法可能误判,用户可反馈"?

**法务需确认**:
1. 误判时责任边界(用户协议 §5 免责条款是否够)
2. 误判反馈机制是否要做(产品 + 法务双重决策)

### 2.4 用户行为审计

**现状**:
- 撤回 / 同意 / 设置变更都写 `user_profiles.consent_*` 字段(本地)
- 没有服务器审计,无法独立证明用户曾同意 / 撤回过什么

**问题**:
- PIPL §24 个人信息处理者应对其处理行为负责
- 假设用户 A 起诉 App"未经同意收集了 X" — 本地审计 log 可信度?

**法务需确认**:
1. 本地审计 log 是否够法律举证?(vs 云端审计 log)
2. 是否需要引导用户截图 / 导出审计 log 作为证据

### 2.5 多语言版本差异

**现状**:
- zh / en / zh_Hant 3 ARB 同步
- 法务 review 重点可能只在 zh,en 和 zh_Hant 是否有差异?

**问题**:
- en 版本可能用了不同法律框架(GDPR / HIPAA),需法务看 en 翻译是否准确
- zh_Hant(港澳台)有不同法律框架(台湾个人资料保护法 / 澳门个人资料保护法)

**法务需确认**:
1. en 版本是否引用 GDPR / CCPA?(当前没引用)
2. zh_Hant 港澳台版本需不需要单独法律声明?

### 2.6 协议变更通知机制

**现状**(`privacy_policy §8` / `user_agreement §7`):
- 重大变更会通过 App 内通知告知
- 继续使用本 App 视为接受变更

**问题**:
- **PIPL §14 单独同意** — "继续使用视为同意"在敏感信息场景下**不适用**,需重新走同意流程
- 法务需确认:协议变更 → 自动重新走同意弹窗?还是只在"重大变更"时弹?

### 2.7 删除权时效响应

**现状**(`sensitive_data_consent §6`):
- 用户主动删除的数据:立即清除
- 用户卸载 App:所有本地数据立即清除
- 7 工作日响应数据删除请求(未成年人 §10)

**问题**:
- PIPL §47 应在 15 个工作日内响应(个别情况可延长至 30)
- 当前 7 工作日(未成年人)**更严格**,合规
- 成年人无明确时效承诺 — 法务需加 15 工作日承诺

### 2.8 数据导出 / 导入风险

**现状**:
- 导出 JSON 是明文,含联系人手机号 + 健康数据 + 树洞文字
- 导入只警告"会覆盖现有数据",没说"覆盖 = 旧数据被物理删除无法恢复"

**问题**:
- PIPL §17 明确告知风险
- 导入覆盖 vs 物理删除 — 措辞准确性

**法务需确认**:
1. 导出后用户自担风险的措辞
2. 导入覆盖 vs 删除的说明

### 2.9 "知情同意" vs "主动使用"
